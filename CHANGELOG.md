# Changelog

## v1.2.6

Released 2026-11-11.

- **License: GNU General Public License, version 3** (was version 2).

## v1.2.5

- BUGFIX: The welcome e-mail greeted every new customer as "Dear Ms." when the store collects gender. Accounts this plugin creates start without one, and the greeting treated anything other than "male" as "female". A customer with no gender on file now gets the neutral "Dear <first name>" greeting; a customer with one set still gets Mr. or Ms.
- BUGFIX: When *Send Copy of Create Account E-Mails To* is turned on, every account added from the admin logged two "Undefined array key "customers_ip_address"" warnings. Zen Cart builds the office-use footer of that copy from a storefront session value that an admin session doesn't have. The plugin now supplies the admin's own IP address for that footer and leaves the session as it found it.

## v1.2.4

- BUGFIX: A new customer's first sign-in showed a confusing message. This plugin creates each account with an empty placeholder address for the customer to replace, and Zen Cart sent them to edit it with "Sorry, but we no longer accept billing or shipping addresses in """. Now they're sent to add their address with "Your account has no address on file. Please add your address to continue." Their first address replaces the placeholder, becomes their primary address, and they go on to the page they were heading for. A customer who already added an address while the placeholder stayed primary is repaired automatically at sign-in, with no extra step.
- BUGFIX: The messages the activation link leaves for the login page never appeared. The customer saw neither the "account activated" confirmation, with its pricing group, wholesale and coupon summary, nor the "invalid or expired link" error. Each one was queued under the wrong message name, so the login page, which shows only its own messages, skipped them. All three now reach the login page.
- CHANGE: The Plugin Manager buttons now read *ReadMe | Forum Thread | GitHub*, in that order, at the same size and spacing as our other plugins, and Forum Thread opens the current support thread, https://www.zen-cart.com/threads/207238, instead of the old forum address.

## v1.2.3

- NEW: Five extension points, so a companion plugin can add its own fields to the single-entry form without this plugin having to know about them. Three cover the form itself - one at the end of each of the Personal, Contact and Options sections, so an added field sits where it belongs rather than in a lump at the bottom - and two cover validating and saving what those fields collect. They follow the same shape Zen Cart core uses for the equivalent feature on its own Categories page, so this page keeps control of its markup and an add-on supplies only the field.
- Nothing about the page changes on its own. With no companion plugin installed, every one of the five is a no-op and the form is exactly what it was in v1.2.2 - this release adds the seams and nothing else.

## v1.2.2

- SECURITY: Customer names shown in the admin's own confirmation messages are now escaped where they're displayed. The names this plugin writes were already stripped of `<` and `>` on the way in, but the *Resend the Welcome E-Mail* message doesn't only show those - its drop-down lists every customer still awaiting activation, including ones who registered through the storefront on an approval-required store, or whose details were edited elsewhere in the admin. This plugin can't vouch for names it didn't write, so it no longer tries to: they're escaped at the point of display instead, which is correct whatever their origin. Reaching this needed an unusual combination (an approval-required store, a customer created outside this plugin with markup in their name, and an admin using Resend on them), so it is hardening rather than an open door.
- CHANGE: `ERROR_BAD_FILE_HEADER` said "recognised"; it now reads "recognized", matching the American spelling used everywhere else.
- CHANGE: The *Welcome E-Mail Header Image* section heading and its *E-Mail Header to Import:* field said "Email" where Zen Cart core writes "E-Mail" (core's own `ENTRY_EMAIL_ADDRESS` is "E-Mail Address:"). Both now match core, along with everything that quotes them - this readme, the CSV formatting guide, and the `email/README.txt`. The readme and CSV guide also mis-quoted core's *Minimum Values->E-Mail Address* setting, which is corrected.
- BUGFIX: The docs said the printable sign-up sheets had to be supplied by the store owner - "you supply them yourself", "Add exactly these two files here before deploying" - but both PDFs have shipped with the plugin since v1.0.0. Anyone following that would have gone looking for files already in their download. Both `readme.html` and `pdf/README.txt` now say the sheets ship and work on install, and explain how to replace either with your own.
- CHANGE: `manifest.php`'s `pluginId` is now declared as an integer rather than a quoted string, matching how Zen Cart's own bundled plugins declare theirs. Nothing behaved differently either way; the value (2445) is unchanged.

## v1.2.1

- SECURITY: The admin page's error panel interpolated its messages into HTML without escaping them. Some of those messages carry a submitted value verbatim (an invalid email address, or a first/last name), and names only pass through `zen_db_prepare_input()` at validation time - the `<>`-stripping `zen_sanitize_string()` isn't applied until the actual insert, which never runs for a row that failed validation. Every value is now escaped at that output boundary, so it's covered regardless of what any current or future message happens to contain.
- SECURITY: The CSV bulk-upload wrote the uploaded file using the client-supplied original filename, unsanitized, as its on-disk path. The `.txt`/`.csv` extension check limited the exposure, but a crafted filename could still place the file outside the intended directory or overwrite an unrelated file. The upload now gets a generated temporary name instead - it's parsed and deleted immediately either way, so its original name was never needed.
- SECURITY: Added the standard `IS_ADMIN_FLAG` direct-access guard to this plugin's admin class file, matching what Zen Cart core uses on its own included admin files. Core's shipped `zc_plugins/.htaccess` already denies direct requests to `.php` files there, but that's Apache-specific and depends on the host permitting `AllowOverride`, so it does nothing on nginx/LiteSpeed or a locked-down shared host.
- BUGFIX: A stale action-name comparison (`insert_multiple`, which no longer matches any action this page actually uses) had silently disabled the uploaded-filename display in the error panel. Corrected - and now escaped, per the first item above.

## v1.2.0

- BUGFIX: `wholesaleEnabled()` called core's `zen_config()` helper, which is only available since ZC v3.0.0 - on any earlier version this fatals with "Call to undefined function," confirmed by a real user report on v2.1.0/PHP 8.2.1. Replaced with a `defined()`/`constant()` check - the same fallback `zen_config()` itself uses internally - so this now behaves identically across the whole v2.0.0-v3.0.0 range this plugin claims to support, not just the versions where `zen_config()` happens to exist.
- BUGFIX: A plugin's own root-level `filenames.php` is only auto-loaded by Zen Cart core starting at v2.2.0 - confirmed directly against core's own bootstrap files at the v2.0.0, v2.1.0, v2.2.0, v2.2.1, and v2.2.2 tags. On v2.0.0/v2.1.0, `FILENAME_ADD_CUSTOMERS`, `BOX_CUSTOMERS_ADD_CUSTOMERS`, `TABLE_ADMIN_ADD_USER_TOKENS`, and (on the storefront) `FILENAME_ADMIN_ADD_USER_ACTIVATE` were never getting defined, breaking the admin menu after install and the activation link in every welcome email - reported by a real user on v2.1.0 as the plugin "not installing." `admin/includes/extra_datafiles/` and `catalog/includes/extra_datafiles/`, unlike root-level `filenames.php`, have been auto-loaded per-plugin since v2.0.0, so a copy of `filenames.php` now lives in each (as a one-line file requiring the original), closing the gap on every version this plugin supports.
- BUGFIX: On a store with core's *New Signup Gift Voucher* setting turned on, every single customer creation (single-entry or CSV) fataled with "Call to undefined function create_coupon_code()" - that function never existed under that name in Zen Cart core, on any version. Replaced with `Coupon::generateRandomCouponCode()`, core's own current replacement, @since exactly the v2.0.0 floor this plugin targets. Found during an audit of every core function this plugin calls, prompted by the two fixes above.

It's now derived from the actual on-disk folder names instead, so it can't go stale on future version bumps.

The listed Author changed from a reference to the original *add_customers_from_admin* mod to "My Zen Cart Host (dbltoe)"; credit to lat9 for that original foundation remains in this readme's introduction above.
- BUGFIX: The new Read Me button pointed at `zc_plugins/AdminAddUser/v1.1.0/readme.html`, but this readme (and the screenshots/CSV-guide it references) only existed at the repository's root, outside the folder the Installation instructions actually have store owners copy - the button would have 404'd on a live store. This readme, its four screenshots, and `add_customers_formatting_csv.html` are now also included inside `zc_plugins/AdminAddUser/v1.1.0/`, alongside the original repository-root copies (kept for browsing before installing).
- CHANGE: In the Bulk Upload (CSV) section, the CSV-formatting help button previously floated in the section's upper-right corner, squeezing the width available for the file field's own "no file chosen" text. It's now positioned at the bottom-left of the section, alongside the Upload button, leaving the file field its full width.
- CHANGE: **Download Blank CSV Template** now sits on its own line above the two **Print Sign-Up Form** buttons, which sit side by side on wide screens and stack one above the other on mobile/tablet.
- CHANGE: The Bulk Upload file field previously used Bootstrap's `col-sm-9 col-md-6` pattern, which narrowed it from 75% to 50% width at desktop screen sizes (992px and up) - on a wide monitor this left too little room for the file field's own "no file chosen" text. It now stays at `col-sm-9` (75%) at every screen size from tablet up.
- BUGFIX/CHANGE: **Print Sign-Up Form (with Wholesale option)**'s label was overflowing straight past its own box on a wide desktop screen - Bootstrap's `.btn` sets `white-space: nowrap`, so no amount of narrowing its column could make the button wrap its own text. Rather than force a wrap, **Print Sign-Up Form** and **Print Sign-Up Form (with Wholesale option)** now each get a dedicated column class (35%/65%, instead of the shared `col-md-6` 50/50 split used by every other two-up field on this page), giving the longer wholesale label enough room to stay on one line within its box.
- CHANGE: The page's own main left/right split (E-Mail Header Image/Bulk Upload/Resend/Delete Unclaimed Signups on the left, Single Customer Entry on the right) previously used Bootstrap's plain `col-md-4`/`col-md-8` (33%/67%). It's now a dedicated 40%/60% split instead - the single-entry fields on the right didn't need two-thirds of the page width, and the left column's own fields (particularly the CSV file field) benefit from the extra room.
- CHANGE: Section headings now also carry a small bottom margin (in addition to their existing top margin), adding a little breathing room between each heading and the fields below it.
- CHANGE: Section headings' font size was set in a fixed 12px by core's admin theme, which doesn't scale with a user's browser/OS text-size or zoom preference - more noticeable on mobile/tablet than desktop. Overridden here in rem instead, and increased to 1.2rem - matching the size core's own `.control-label` already uses elsewhere in this admin theme - for noticeably easier reading without crowding the page.
- CHANGE: Field help text (`.help-block`) now also uses that same 1.2rem, matching the labels it belongs to.
- BUGFIX: Field labels (`.control-label`) weren't reliably showing at core's own intended 1.2rem on this page, confirmed via live inspection. Now explicitly set here too, the same way as the other overrides above.
- CHANGE: Form fields themselves (inputs, selects, textareas - most visibly the "Please Choose" placeholder in the Resend the Welcome E-Mail customer dropdown) were set to a fixed 11px by core's shared stylesheet. Brought up to the same 1.2rem as the rest of this page's text.
- BUGFIX: The "Reset the Customer's Password?" checkbox carried a `form-control` class, which is meant for block-level, full-width text inputs/selects - it rendered the checkbox oversized, more like a button than a checkbox. Removed; the checkbox now renders at its normal size.
- CHANGE: Fixed the "encapsulated plugin" link (both here and in the Version History entry below) - it pointed at `/dev/plugins/encapsulated_plugins/`, which no longer resolves; the correct current path is `/dev/plugins/encapsulated/`.
- CHANGE: `manifest.php`'s Plugin Manager info box now also shows a plain **Forum Support Thread** link, below the existing Read Me/GitHub buttons, pointing to this plugin's own support thread (https://www.zen-cart.com/threads/207238).
- CHANGE: `manifest.php`'s `pluginId` updated from `1477` (lat9's original *add_customers_from_admin* listing) to `2445`, this plugin's own new listing on the Zen Cart Plugins Library.
- CHANGE: Added a `.gitattributes` file forcing PDFs and image files to always be treated as binary. Both sign-up-sheet PDFs are hand-built with an uncompressed content stream, so git's own text/binary heuristic (which looks for a NUL byte in the first 8000 bytes) can misjudge them as text - on a fresh clone with line-ending conversion enabled, that would silently rewrite bytes inside the file and corrupt it, producing a PDF that viewers refuse to open.

## v1.0.0

- CHANGE: Supported Zen Cart versions are now v2.0.0 through the current v3.0.0-track `master` (dropping v1.5.x support; there is no separate v2.3.0 release to target).
- CHANGE: Repackaged as an encapsulated plugin (https://docs.zen-cart.com/dev/plugins/encapsulated/) under `zc_plugins/AdminAddUser/`, installed/uninstalled via the admin's Plugin Manager. No files are copied into or overwrite anything in `YOUR_ADMIN`.
- CHANGE: Reworked into a pending-activation flow (see "How Activation Works" above): new customers now always start pending and are emailed an activation link, rather than being created immediately-active. The "Customers Authorization Status" dropdown, gender, date of birth, company, suburb, email-format preference, newsletter, and referral-coupon fields were removed from the single-entry form (deferred to the customer's own completion step); the "send welcome email" option was removed since sending it is now mandatory (it's the only way the customer gets their activation link).
- CHANGE: Both the single-entry form and CSV bulk-upload are now trimmed to the bare minimum: First Name, Last Name, and E-Mail are the only required fields - Telephone is optional (the customer can add or correct it at activation), and Address, Tax/Resale Number, gender, date of birth, and company are never collected at entry at all, only at activation. Coupon assignment was removed from both entry points entirely; it may return later as an option on *Resend the Activation E-Mail* instead.
- NEW: Optional *Wholesale* level field (single-entry form and CSV column `wholesale_level`), using core's own `customers_whole` field (built in since Zen Cart v2.0.0) and gated on the store's existing *Wholesale Pricing* setting - no new Configuration page added. Zen Cart core defines no fixed list of what each level means; it's a plain number (0 for none) matching whatever pricing scheme the store already has in place.
- NEW: `Customers->Add Customer(s)` now adds a storefront page (reached via the activation email link) where the customer reviews their assigned group/wholesale level and completes whatever your store's configuration requires. This plugin uses its own activation-token table rather than Zen Cart core's built-in one (that one only exists since v2.2.0).
- CHANGE: Removed the CSV bulk-upload's *Insert Mode* choice ("Part" vs "File"). With the field set this minimal, a failing row is almost always an isolated typo rather than a sign of a bad file, so every valid row is now inserted immediately as it's found; a bad row is flagged and skipped without holding up anyone else's activation email.
- BUGFIX: The `customers` table insert was missing the `customers_nick`, `registration_ip`, and `last_login_ip` columns, which have been required (`NOT NULL`, no default) since Zen Cart v2.0.0. Under a database running in strict SQL mode (the modern MySQL 8 / MariaDB default), this caused every "add customer" attempt to fail outright.
- BUGFIX: Loading a plugin's own class file, page-specific language file, and content template from a brand-new catalog page all fatally errored on a real click-through - Zen Cart's catalog page loader isn't zc_plugins-aware for any of those the way the admin router is for admin pages. Rather than working around each one, the whole custom completion page and its content template were dropped: clicking the activation link now activates the account immediately and hands the customer off to your storefront's own login page - a completely standard Zen Cart login/account/address-book experience needing no catalog page or template of this plugin's own at all. See "How Activation Works" above. The Tax / Resale Number field, previously only collected on that now-removed completion page, moved back to the single-entry admin form (its only remaining entry point).
- NEW: *Delete Unclaimed Signups* tool - since activation no longer waits on the customer completing their profile, this permanently removes customers registered before a chosen date who never ended up with a complete address on file. See "Delete Unclaimed Signups" above.
- NEW: Optional header banner image for the welcome/activation email's HTML version, matching core's own `images/header.jpg` convention - see "Welcome E-Mail Header Image (optional)" above.
- CHANGE: Renamed the admin menu entry and page title from "Add Customer" to "Add Customer(s)", since the tool has always handled bulk upload as well as single-entry.
- BUGFIX/CHANGE: Accessibility pass on the admin page (WCAG A/AA): section titles were plain styled `<div>`s, invisible to screen-reader heading navigation - they're now real `<h2>`/`<h3>` elements (same visual styling, same CSS class). The CSV help icon-link had no accessible name beyond an unreliable `title` attribute - added an explicit `aria-label`. The current-header-image preview had an empty `alt` despite being informative, not decorative - given a real one. The error-summary box is now marked `role="alert"`, and the page's own content is wrapped in a `role="main"` landmark.
- BUGFIX: Every form field's `<label>` pointed at a `for=` value with no matching `id` on the actual field - inputs, dropdowns, and the checkbox alike - since none of core's `zen_draw_input_field()`/`zen_draw_file_field()`/`zen_draw_pull_down_menu()`/`zen_draw_checkbox_field()` set one automatically. The label was never actually programmatically associated with its field despite looking correct visually. All twelve affected fields now get an explicit `id`. Also corrected color contrast to meet AA (and, where free to do so, AAA): `.help-block` text, the primary/danger button colors (with matching hover/focus states), and the required-field asterisk. Interactive elements (buttons and button-styled links) are now at least 44 x 44px, since several of the smaller ones fell short of that on mobile/tablet.
